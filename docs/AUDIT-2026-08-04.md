# Novaframe Engine — Full Audit

**Date:** 2026-08-04
**Version audited:** 0.4.6 (`main` @ `bee97a5`, clean tree)
**Scope:** `src-tauri/` (Rust, 1971 LOC), `src/` (frontend, 2 545 LOC), capabilities, CSP, CI/release pipeline, bundled runtime.
**Verified:** `cargo check` passes clean, `npm audit` clean (0 vulns), ACL resolution traced against `tauri-2.11.3` source.

Two risk numbers per finding:

- **Risk if left** — probability this actually hurts you (likelihood × blast radius) before you cross ~1 000 installs.
- **Fix risk** — probability the fix itself breaks something.

---

## Executive summary

The Rust backend is in better shape than most Tauri apps of this age: path traversal is properly defended (`installer.rs:385`, `theme_protocol.rs:68-99`), the theme iframe is correctly sandboxed without `allow-same-origin` (`themeManager.js:175`), the invoke key is main-frame-only so a malicious theme cannot reach IPC, and remote origins are correctly blocked from custom commands. Those are the things that usually go wrong, and they didn't.

The problems are elsewhere, and two of them are business-critical rather than technical:

1. **You ship unsigned, un-notarized installers.** Every macOS user hits a Gatekeeper block; every Windows user hits SmartScreen. This is almost certainly costing you installs right now, and it probably breaks macOS auto-update for existing users.
2. **The marketplace website has an IPC channel into the desktop app.** `capabilities/storefront.json` hands `core:default` — which includes `core:event:allow-emit` — to `novaframe.co.uk`. One XSS on your own site becomes control of every user's engine event bus. The storefront needs no IPC at all.

Then a set of things that will bite as you scale: an unbounded debug log written on every mouse click, a "Power Saver" FPS setting that doesn't reduce wakeups and undershoots its own target by 20 %, ~6 MB of dead assets in every installer and every update download, and a release pipeline with a non-atomic publish step.

**Fix order: A1 → A2 → A3 → A4 → B5 → C1 → D1 → everything else.**

## A. Urgent — fix before the next release

### A1. The marketplace website can inject events into the privileged desktop windows

**Severity: Critical** · **Risk if left: 35 %** · **Fix risk: 5 %**

`src-tauri/capabilities/storefront.json` grants `core:default` to remote origins `https://www.novaframe.co.uk/*` and `https://novaframe.co.uk/*`. Resolved against `gen/schemas/acl-manifests.json`, `core:default` expands to include:

```
core:event  -> allow-listen, allow-unlisten, allow-emit, allow-emit-to
core:window -> allow-get-all-windows, allow-cursor-position, allow-available-monitors, +23 more
core:webview, core:app, core:path, core:image, core:menu, core:tray, core:resources
```

`allow-emit` is the problem. Any JavaScript executing on the storefront origin — a stored XSS in a wallpaper title rendered on `/explore`, a compromised third-party analytics or embed script, a dependency-confusion hit on the Next.js bundle — can call:

```js
window.__TAURI_INTERNALS__.invoke('plugin:event|emit', { event: '<any>', payload: <any> })
```

and that event is delivered to the `main` and `settings` webviews, which listen for it as trusted internal state. Confirmed reachable listeners in `src/app.js`:

| Injected event | Handler | Effect |
|---|---|---|
| `occlusion-change` (false) | `app.js:1087` | Wallpaper set to `display:none` permanently. No UI recovers this; product looks dead. |
| `config-changed` | `app.js:1062` | Attacker object becomes `config`, persisted to the native store on next save. |
| `engine-apply-theme` | `app.js:970` | Engine POSTs attacker payload to `verify-token` **with the real machine-uid**, then installs whatever `downloadUrl` the response carries. Forced-install / DoS. |
| `theme-installed` | `app.js:1051` | Forced theme switch to an attacker-chosen path + `window.location.reload()` — trivially loopable into a reload storm. |
| `theme-changed` / `theme-reload` / `theme-action` | `app.js:1033-1077` | Forced remount, message flooding into the theme iframe. |

This is not remotely triggerable by an arbitrary website — it requires code execution on your own origin. But that is exactly the threat you should assume for a site that renders user-adjacent content and loads third-party scripts, and the blast radius is every installed engine simultaneously.

**The storefront window needs zero IPC.** The entire apply flow runs through `window.rs:163-169`, which intercepts `novaframe://` in `on_navigation` and never touches the webview's IPC bridge.

**Fix**

1. Delete `src-tauri/capabilities/storefront.json` outright.
2. Remove `"storefront"` from the `windows` array in `src-tauri/capabilities/default.json:5` — that capability is `local: true`, and the storefront window only ever loads remote content, so the entry is dead weight that reads as an intentional grant.
3. Rebuild and confirm the marketplace still opens, browses, and that clicking Apply still installs (it goes through the deep-link path, not IPC).

If some future storefront feature genuinely needs one command, add a capability naming that single permission — never `core:default`.

### A2. Installers are unsigned and un-notarized

**Severity: Critical (commercial)** · **Risk if left: 95 % — this is already costing you** · **Fix risk: 10 %**

`.github/workflows/release.yml:41-42` sets `TAURI_SIGNING_PRIVATE_KEY`. That is the **minisign updater key**, which signs the update manifest — it is *not* code signing. There is no `APPLE_CERTIFICATE`, `APPLE_ID`, `APPLE_PASSWORD`, `APPLE_TEAM_ID`, and no `WINDOWS_CERTIFICATE`. `src-tauri/tauri.conf.json`'s `bundle.macOS` block contains only `infoPlist` — no `signingIdentity`, no `entitlements`, no hardened runtime.

Consequences for a paying customer downloading your `.dmg`:

- **macOS**: the download is quarantined. An unsigned app fails Gatekeeper validation. Depending on macOS version the user sees either "Novaframe can't be opened because Apple cannot check it for malicious software" or the harsher "Novaframe is damaged and can't be opened. You should move it to the Trash." On Sequoia and later, the old right-click → Open bypass no longer works; the user must go to System Settings → Privacy & Security and click "Open Anyway", or run `xattr -dr com.apple.quarantine`.
- **Windows**: unsigned `.exe` triggers the full-screen SmartScreen "Windows protected your PC" interstitial, where the "Run anyway" button is hidden behind "More info".

You are asking someone who just paid you to talk their way past an OS-level malware warning. Signing is the highest-ROI item in this document.

**Fix**

1. Apple Developer Program ($99/yr) → Developer ID Application certificate. Export as `.p12`, base64 it into GitHub secrets. Add to `release.yml`:
   ```yaml
   APPLE_CERTIFICATE: ${{ secrets.APPLE_CERTIFICATE }}
   APPLE_CERTIFICATE_PASSWORD: ${{ secrets.APPLE_CERTIFICATE_PASSWORD }}
   APPLE_SIGNING_IDENTITY: ${{ secrets.APPLE_SIGNING_IDENTITY }}
   APPLE_ID: ${{ secrets.APPLE_ID }}
   APPLE_PASSWORD: ${{ secrets.APPLE_PASSWORD }}     # app-specific password
   APPLE_TEAM_ID: ${{ secrets.APPLE_TEAM_ID }}
   ```
   `tauri-action` notarizes automatically once `APPLE_ID` + `APPLE_PASSWORD` + `APPLE_TEAM_ID` are present.
2. Windows: **Azure Trusted Signing** (~$10/mo, no hardware token, no EV cert purchase) is the current path of least resistance. Configure via `bundle.windows.signCommand` in `tauri.conf.json`.
3. Verify on a machine that has never seen the app: download from the real Supabase URL, double-click, confirm no warning. `spctl -a -vvv /Applications/Novaframe.app` should print `accepted, source=Notarized Developer ID`.

Fix risk is 10 % rather than 0 % because a wrong entitlements file can break the desktop-underlay window or the deep-link scheme registration — test the full flow after enabling.

### A3. macOS auto-update is probably broken in the field

**Severity: Critical** · **Risk if left: 60 %** · **Fix risk: — (subsumed by A2)**

Direct consequence of A2, but it needs its own line because the failure mode is worse than a first-install warning: it strands existing users.

Tauri's macOS updater downloads a `.app.tar.gz` and replaces the installed bundle in place. Gatekeeper re-evaluates the replaced bundle on next launch. An unsigned replacement is very likely to be rejected — meaning a user who clicks your "Restart to Apply Update" button ends up with an app that will not start, and no path back except a manual re-download they don't know they need.

This will not reproduce in `tauri dev` or from a locally-built `.dmg`, because local builds are ad-hoc signed by Xcode and never carry the quarantine attribute. It only shows up on a machine that downloaded the artifact over the network.

**Fix:** ship A2, then explicitly test the upgrade path — install the *published* `.dmg` on a clean macOS machine (or a fresh VM), let it auto-update to the next version, quit, relaunch. Do not cut another release until that passes.

### A4. Single point of failure in the updater endpoint

**Severity: High** · **Risk if left: 30 %** · **Fix risk: 5 %**

`src-tauri/tauri.conf.json` declares exactly one updater endpoint:

```json
"endpoints": ["https://api.novaframe.co.uk/api/engine/updates/{{target}}/{{current_version}}"]
```

If that host goes down, the route regresses, the TLS cert lapses, or the domain renewal is missed, every installed engine permanently loses auto-update. The recovery mechanism for a broken updater *is* the updater — so there is no push fix. You would have to email every customer and ask them to reinstall by hand.

**Fix:** Tauri accepts an array and tries endpoints in order. Add the GitHub Releases `latest.json` (already produced by `createUpdaterArtifacts: true`) as a fallback:

```json
"endpoints": [
  "https://api.novaframe.co.uk/api/engine/updates/{{target}}/{{current_version}}",
  "https://github.com/<owner>/<repo>/releases/latest/download/latest.json"
]
```

Both are validated against the same minisign pubkey, so the fallback adds no trust surface. Costs one line.

## B. Fix before user count grows

### B1. `theme://` responds `Access-Control-Allow-Origin: *` — purchased wallpaper source is cross-origin readable

**Severity: High** · **Risk if left: 20 %** · **Fix risk: 10 %**

`src-tauri/src/theme_protocol.rs:41` and `:122` set `Access-Control-Allow-Origin: *` on every response, including the 200 path that serves theme source.

The custom scheme handler is registered on the whole app, so it is reachable from every webview — including the remote storefront window, and (given B2) any site that window navigates to. A wildcard ACAO means such a page can `fetch('theme://localhost/<path>')` and read the raw GLSL, JS and image assets of every wallpaper the user has purchased.

Those assets are the product. This is a direct exfiltration path around the DRM/device-locking work.

**Fix**

1. Read the request's `Origin` header. Reflect ACAO only for `tauri://localhost` (macOS/Linux) and `http://tauri.localhost` (Windows); return 403 for any other origin.
2. Keep the existing canonicalize-and-allowlist check as-is — it is correct.

Fix risk is 10 % because the main window fetches manifests cross-scheme and WebView2 vs WKWebView send different `Origin` values for custom schemes. Test manifest loading on both platforms after the change.

### B2. The storefront window can navigate anywhere

**Severity: Medium-High** · **Risk if left: 15 %** · **Fix risk: 15 %**

`src-tauri/src/window.rs:163-170`:

```rust
.on_navigation(move |nav_url| {
    let s = nav_url.as_str();
    if s.starts_with("novaframe://") { … return false; }
    true          // ← everything else is allowed
})
```

Any link — an open redirect on the marketplace, a compromised ad or embed, a typo'd outbound URL — walks the user into an arbitrary page rendered inside a decorated, native-chrome window titled "Novaframe Marketplace". That is a high-credibility phishing surface for marketplace credentials, and it is also how an attacker-controlled origin gets into position to exploit B1.

**Fix:** allowlist the hosts the storefront genuinely needs (`novaframe.co.uk`, `www.novaframe.co.uk`, plus whatever Stripe / Supabase auth hosts checkout redirects through), return `false` for everything else, and hand rejected URLs to the system browser via `tauri_plugin_opener`.

Fix risk is 15 % specifically because Stripe Checkout and any OAuth sign-in bounce through third-party hosts — enumerate the real redirect chain before tightening, or you will break purchases.

### B3. Unbounded download and zip extraction

**Severity: Medium** · **Risk if left: 10 % today, 100 % if anything upstream is compromised** · **Fix risk: 5 %**

`installer.rs:343-375` (`download_to_file`) streams the response to disk with no `Content-Length` check and no byte cap. `installer.rs:227-231` extracts each zip entry with `std::io::copy` — no cap on per-entry size, total extracted bytes, or entry count.

A 1 MB zip of compressed zeroes expands to hundreds of GB. Nothing stops it. Symptom: the user's disk fills and macOS/Windows start failing system-wide, from a wallpaper install.

Today the URL comes from your own backend's `verify-token` response, and remote origins are correctly blocked from calling this command — so it is not currently attacker-reachable. It is one backend bug away from being so, and a plain wrong URL causes the same disk-fill accidentally.

**Fix**

- Cap the download at a sane ceiling (200 MB) — abort the stream once exceeded.
- Track cumulative extracted bytes and entry count across the loop; abort past 500 MB or 5 000 entries.
- Validate the download URL's host against your storage domain before fetching.

### B4. Zips with a wrapper folder install one directory too deep and silently vanish

**Severity: Medium (correctness)** · **Risk if left: 25 %** · **Fix risk: 10 %**

`installer.rs:234-252`, `find_manifest_dir` correctly handles a zip whose manifest sits inside a top-level folder, returning `staging_dir/<subdir>`. But `installer.rs:318` then renames the **wrong directory**:

```rust
fs::rename(&staging_dir, &named_dir)     // moves staging, not target_dir
```

Result on disk: `<themes>/<slug>/<subdir>/manifest.json`. `scanThemes` (`app.js:720-723`) reads `<themesDir>/<entry.name>/manifest.json` and finds nothing — so a purchase that reported success never appears in the dropdown, with no error anywhere the user can see.

Second-order: `.nova_meta.json` is written into `target_dir` (`installer.rs:308`), but the dedupe lookup `read_marketplace_id(&named_dir)` (`installer.rs:277`) reads the level above it. So it always misses, and every re-apply of the same wallpaper creates `slug-2`, `slug-3`, `slug-4`… forever.

Your current `package_themes.py` produces flat zips, so this is latent — until one zip is built differently, or a theme is packaged by hand.

**Fix:** rename `target_dir` into place rather than `staging_dir`. The `TempDirGuard` on `staging_dir` (`installer.rs:336`) then cleans up the now-empty wrapper automatically.

### B5. Unbounded debug log, written on every mouse click

**Severity: Medium** · **Risk if left: 40 %** · **Fix risk: 3 %**

`main.rs:157-174` — `dlog` opens `AppData/engine-debug.log`, appends, and closes on every single call. Nothing rotates it, truncates it, or deletes it. Ever.

Three hot paths call it:

1. **Every mouse click, anywhere, in either window.** `src/app.js:1159-1164` registers a capture-phase `click` listener on `document` that fires `invoke('log_from_js', …)` unconditionally. That is a full IPC round trip plus a file open/write/close per click. It is labelled "Global DOM Click Diagnostic Listener" — it is a debugging aid that shipped.
2. **Every `theme://` request**, both 200 (`theme_protocol.rs:116`) and 404 (`:71`). A theme fetching shaders, textures and manifests generates a disk write per asset.
3. Startup, layout, and pause transitions — those are fine and worth keeping.

On a machine left running for months, this file grows without bound in the user's AppData with no cleanup path.

**Fix**

- Delete the global click listener at `app.js:1159-1164` entirely. It has no production purpose.
- Gate the per-request `theme://` logging behind `#[cfg(debug_assertions)]`.
- Add rotation to `dlog`: if the file exceeds ~2 MB, rename to `engine-debug.log.old` (overwriting any previous) and start fresh. Keeps field diagnostics, caps disk at ~4 MB.

### B6. Hovering the right screen edge steals focus from whatever you're typing in

**Severity: Medium (UX)** · **Risk if left: 70 %** · **Fix risk: 15 %**

`window.rs:128-133`, `expand_settings_panel` calls `window.set_focus()` unconditionally, and the hover poll loops (`main.rs:853`, `:903`) call it on every hover transition. Moving the mouse toward the right edge of the screen — a thing people do constantly, e.g. reaching for a scrollbar — activates Novaframe and pulls focus out of the app the user was typing in.

Compounding it: there is no `LSUIElement` in `src-tauri/Info.plist` and no `ActivationPolicy::Accessory` anywhere in the Rust. So on macOS the engine also owns a Dock icon and swaps the menu bar on every one of those accidental activations — for an app whose own onboarding copy says "Novaframe has no window".

**Fix**

- Set `ActivationPolicy::Accessory` at startup on macOS (or `LSUIElement` in `Info.plist`). Removes the Dock icon and the menu-bar takeover; the tray icon already covers discoverability.
- Only call `set_focus()` from the explicit paths — the tray "Show Settings" item (`window.rs:43`) — not from the hover expansion.

Fix risk 15 %: without focus, keyboard interaction inside the panel (typing in a colour picker, Escape to close a modal) may need re-testing. Verify the modal Enter/Escape handlers in `app.js:850` still work.

## C. Performance

### C1. "Power Saver" doesn't reduce wakeups, and undershoots its own target by ~20 %

**Severity: High (it's your headline feature)** · **Risk if left: 50 %** · **Fix risk: 15 %**

`src-tauri/resources/default-theme/novaframe-wallpaper.js:83-108` — this file is served to **every** theme via the protocol interception at `theme_protocol.rs:104-112`, so this affects all 48 shipped wallpapers at once.

```js
function loop(now) {
  if (!isActive()) { rafId = null; return; }
  rafId = global.requestAnimationFrame(loop);              // ← always reschedules
  if (frameInterval && now - lastDraw < frameInterval) return;
  …
}
```

**Problem 1 — the wake rate never drops.** rAF is rescheduled every frame regardless of target FPS. On a 120 Hz display at "30 FPS (Power Saver)", the JS thread and compositor still wake 120 times a second; you skip the *draw*, not the *wake*. The saving is real but far smaller than the label implies.

**Problem 2 — the gate has no tolerance, so the effective rate collapses.** At 120 Hz, `frameInterval = 33.33 ms` and frame boundaries land at multiples of 8.33 ms. The boundary at 33.32 ms fails `< 33.33`, so the draw slips to the next one at 41.65 ms:

```
1000 / 41.65 = 24 FPS delivered, for a 30 FPS setting
```

The same undershoot occurs at every target that isn't an exact divisor of the display refresh rate. On a 144 Hz panel it's worse.

**Fix**

Implemented as four changes in `novaframe-wallpaper.js`:

1. **Learn the display refresh period** from the gap between consecutive rAF callbacks (smallest recent gap wins — a gap can be stretched by a slow frame, never shortened below the true period).
2. **Draw at the boundary nearest the deadline**, not the one after it: gate on `now < nextDrawAt - refreshMs / 2`.
3. **Advance the deadline on a fixed grid** (`nextDrawAt += frameInterval`) rather than from `now`, so per-frame error doesn't accumulate. This is what lets a target that isn't a whole divisor of the refresh rate average out correctly — 30 fps on 144 Hz alternates 4- and 5-frame gaps instead of locking to one. Resyncs when more than a full interval behind, so a throttled or slept machine doesn't burst to catch up.
4. **Sleep on a timer** when the wait exceeds one refresh, and only then request a frame.

**Measured** with a simulated-clock harness, 10 simulated seconds per case. "Wakeups" counts every scheduled callback — that is the power cost:

| Display | Target | Delivered before | Delivered after | Wakeups/s before | Wakeups/s after |
|---|---|---|---|---|---|
| 60 Hz | 30 fps | 20.5 | **30.0** | 60 | 60 |
| 120 Hz | 30 fps | 26.7 | **30.1** | 120 | **60** |
| 144 Hz | 30 fps | 28.8 | **30.1** | 144 | **60** |
| 120 Hz | 60 fps | 40.1 | **60.0** | 120 | 120 |
| 60 Hz | 60 fps | 39.6 | **60.0** | 60 | 60 |

The undershoot was worse than reading alone suggested: a plain 60 Hz display was delivering **20.5 fps for a 30 fps setting**. Every case now hits its target, and the wakeup rate on high-refresh displays halves.

Still worth a real-device check across a few themes with different render approaches (WebGL, 2D canvas, CSS animation) before shipping, since this file is served to all of them.

### C3. Windows idle CPU: full window enumeration every 800 ms

**Severity: Medium** · **Risk if left: 35 %** · **Fix risk: 10 %**

`main.rs:563-591` spawns a thread that calls `desktop_is_covered()` (`main.rs:343-455`) every 800 ms. Each call runs `EnumDisplayMonitors` + `EnumWindows`, and per top-level window: `IsWindowVisible`, `IsIconic`, `GetWindowThreadProcessId`, `DwmGetWindowAttribute`, `GetClassNameW`, `GetWindowRect`. On a working desktop with 150–300 top-level windows that is well over a thousand syscalls per second, permanently, in an app that is supposed to be invisible.

The logic itself is right and the fullscreen short-circuit at `main.rs:582` helps — but the common case (not fullscreen) is the one that runs the expensive path.

**Fix**

- Cheapest: adaptive backoff. Once the covered state has been stable for ~5 cycles, poll every 3 s; drop back to 800 ms on any change.
- Better: drive it from `SetWinEventHook` on `EVENT_SYSTEM_FOREGROUND` + `EVENT_OBJECT_LOCATIONCHANGE` and only enumerate when the foreground window actually changed.

### C4. Windows/Linux hover poll has no proximity backoff

**Severity: Medium** · **Risk if left: 30 %** · **Fix risk: 5 %**

The macOS hover loop backs off correctly — `main.rs:848` sleeps 100 ms when the cursor is near the panel and 800 ms when it isn't. The non-macOS loop (`main.rs:867-910`) polls a **fixed 150 ms forever**, and each tick makes three runtime calls (`cursor_position`, `outer_position`, `outer_size`). That is ~7 polls and ~20 runtime calls per second, permanently, on your majority platform.

**Fix:** mirror the macOS logic — compute proximity from the cursor X against the panel's left edge, sleep 150 ms when near and 800 ms when not. Cache `outer_position`/`outer_size` between ticks and refresh them only when the layout pass runs.

### C5. macOS hover poll bounces off the AppKit main thread every second

**Severity: Low** · **Risk if left: 15 %** · **Fix risk: 20 %**

`main.rs:821-847` dispatches to `run_on_main_thread` and then blocks on an `mpsc` channel for the result, every 800–1000 ms, forever. Individually cheap, but it is work on the UI thread that never stops, and the synchronous `rx.recv()` means the poll thread is pinned waiting on main-loop availability.

**Fix:** cache the panel frame (it only changes in `place_settings_window`) and read `NSEvent.mouseLocation` — which is process-global and does not require the window — so the common case needs no main-thread hop at all.

Fix risk 20 %: AppKit thread-safety assumptions are easy to get wrong here. Low reward; do it last, or leave it.

### C6. Blocking file I/O inside an async command, under a lock, for up to 180 s

**Severity: Low-Medium** · **Risk if left: 20 %** · **Fix risk: 5 %**

`installer.rs:44-92` and `:128-327` — `download_and_install_theme` is `async` and holds `INSTALL_MUTEX` (`installer.rs:42`) across the whole operation, but the extraction does synchronous `fs::File::create`, `std::io::copy` per entry, `fs::rename`, and `fs::remove_dir_all` directly on a tokio worker thread. The HTTP client timeout is 180 s (`installer.rs:159`), so a slow CDN pins a runtime worker for three minutes while blocking file work interleaves on it.

**Fix:** wrap everything from `fs::File::open(&temp_zip_path)` (`installer.rs:193`) through the final `fs::rename` in `tokio::task::spawn_blocking`.

### C7. Monitor configuration polled every 2 s forever

**Severity: Low** · **Risk if left: 10 %** · **Fix risk: 10 %**

`main.rs:667-723` calls `available_monitors()` every 2 s, formats every monitor's position/size/scale into a `String`, and compares. Plus, on Windows, `inner_size()` + `current_monitor()` for the drift check. Allocation and OS enumeration on a fixed 2 s tick, forever.

**Fix:** slow the base poll to 10 s. The Windows drift-correction retry burst at `main.rs:773-782` already covers the startup reparent race, which is the case that actually needs sub-second reaction.

### C8. Google Fonts fetched from the network on every launch

**Severity: Low-Medium** · **Risk if left: 40 %** · **Fix risk: 3 %**

`src/index.html:7-9` preconnects and `<link>`s the Outfit family from `fonts.googleapis.com` / `fonts.gstatic.com`. Four consequences:

- A network round trip on every app start, on the critical path to first paint.
- Offline or slow network → fallback font, visibly wrong panel typography.
- Every user's desktop pings Google on every launch. For a paid desktop product that is a privacy detail worth not having, and in the EU it is a GDPR question you don't need.
- It is the only reason `tauri.conf.json`'s CSP has to allowlist two Google origins in both `default-src` and `style-src`.

**Fix:** self-host the two or three weights you actually use as `.woff2` under `src/assets/fonts/`, declare `@font-face` in `style.css`, and delete both Google origins from the CSP. Smaller CSP, faster start, works offline.

## E. Release pipeline

### E1. The Supabase publish step is non-atomic and unverified

**Severity: Medium** · **Risk if left: 20 % per release** · **Fix risk: 5 %**

`.github/workflows/release.yml`, `mark version as latest in engine_releases`:

```bash
curl -sf -X PATCH "…/engine_releases?is_latest=eq.true" -d '{"is_latest": false}'   # demote all
curl -sf -X POST  "…/engine_releases" -d "{…, \"is_latest\": true}"                 # insert new
```

Demote-then-insert. If the POST fails — network blip, schema change, RLS policy, malformed JSON — **no row is `is_latest`**, and the storefront `/download` page has nothing to serve. There is no rollback, no retry, and no check afterwards. You would find out from a customer.

**Fix**

1. Reverse the order: insert the new row first, then demote everything else (`is_latest=eq.true&version=neq.$VERSION`). Worst case is two latest rows, which degrades to "serves one of two good versions" instead of "serves nothing".
2. Add a verification step: `GET …/engine_releases?is_latest=eq.true` and fail the job unless it returns exactly one row matching `$VERSION`.

---

### E2. CI gates compilation only

**Severity: Medium** · **Risk if left: 25 %** · **Fix risk: 5 %**

`.github/workflows/ci.yml` runs `cargo check` on Windows and macOS — genuinely the right call given how heavily `#[cfg(target_os)]`-gated this codebase is, and it currently passes clean.

What it does not do:

- `clippy` and `rustfmt` are both `continue-on-error` (`ci.yml:44`, `:48`). The comment says to flip them once the debt is cleared. `cargo check` is clean today, so the clippy debt is likely small — worth measuring and flipping.
- **No `cargo test`.** There are three unit tests total (`main.rs:920-949`), covering `is_safe_theme_name` and deep-link token decoding. They aren't run by CI at all.
- No frontend build check. `npm run build` only runs during a release, so a syntax error in `app.js` reaches a tag before anyone notices.
- **Nothing tests the install path** — which is exactly where B3 and B4 live.

**Fix**

1. Add `cargo test --manifest-path src-tauri/Cargo.toml` to `ci.yml`.
2. Add `npm ci && npm run build` as a job so bundle breakage fails the PR.
3. Add unit tests for the zip extraction: flat zip, wrapper-folder zip (currently fails — B4), zip with a `__MACOSX` entry, oversized entry (currently fails — B3).
4. Once clippy's real count is known, drop `continue-on-error`.

---

### E3. No published checksums

**Severity: Low** · **Risk if left: 10 %** · **Fix risk: 3 %**

The Supabase-hosted `.exe`/`.dmg` have no SHA-256 alongside them, so a user who wants to verify their download can't, and a corrupted upload is undetectable until someone runs it. Emit `sha256sum` into the `engine_releases` row during the sync step.

## What's already right

Worth recording so nobody "fixes" it later:

- **Theme iframe sandbox** (`themeManager.js:175`): `sandbox="allow-scripts"` without `allow-same-origin` gives themes a null origin — no storage, no same-origin reads, no path to the parent. Correct.
- **Invoke key is main-frame-only** (verified against `tauri-2.11.3/src/manager/webview.rs:182`), so a malicious theme iframe cannot forge IPC even though `theme://` classifies as a local origin. Two independent defences; keep both.
- **Path traversal** is properly handled in both directions: `is_safe_theme_name` + canonicalize + prefix check in `delete_theme` (`installer.rs:385-418`), and canonicalize-against-allowlisted-roots in the theme protocol (`theme_protocol.rs:68-99`). Both have tests.
- **Remote origins cannot reach custom commands** — confirmed at `tauri-2.11.3/src/webview/mod.rs:1826`: the ACL check fires for any non-local origin regardless of whether an app ACL manifest exists. A1 is about the `core:*` plugin commands you explicitly granted, not a hole in this.
- **Dev-only path allowlisting** (`theme_protocol.rs:85-90`) correctly keeps a personal filesystem path out of release binaries via `#[cfg(debug_assertions)]`.
- **CSP is genuinely restrictive**: `script-src 'self'`, `object-src 'none'`, `base-uri 'none'`. The inline-script extraction into `mode-init.js` to satisfy it was the right call rather than adding `'unsafe-inline'`.
- **Cross-platform CI matrix** on Windows + macOS is the correct shape for a codebase this `cfg`-gated, and it currently passes clean with zero warnings.
- The comment quality in `main.rs` and `installer.rs` — particularly the ones explaining *why* something is async, or why occlusion state is meaningless at desktop window level — is well above average and made this audit substantially faster.
